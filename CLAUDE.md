# PodoPrev

App de triagem podológica preventiva para diabéticos — TCC de Sistemas de Informação. React + TypeScript + Firebase + Capacitor.

Não é sistema clínico/diagnóstico: classifica em "nível de atenção" (baixo/médio/alto), nunca "risco médico" ou diagnóstico. Todo texto de resultado deve manter esse tom.

## Stack

- React 19 + TypeScript + Vite 8 + React Router 7
- Firebase: Auth (Email/Password) + Firestore. **Storage NÃO configurado** de propósito (exige plano Blaze/cartão) — fotos caem em armazenamento local (`isStorageConfigured` em `src/firebase/config.ts`).
- Capacitor (Android) — não testado extensivamente ainda.
- jsPDF para relatórios de atendimento.

## Projeto Firebase

- Projeto: **podeprev** (nome com erro de digitação, intencional/aceito — não mexer).
- Hosting: **https://podeprev.web.app** (produção, Firebase real) e **https://podeprev-demo.web.app** (site separado, sempre com o build em modo demonstração — ver abaixo). Dois sites de Hosting dentro do mesmo projeto Firebase, mapeados em `.firebaserc`/`firebase.json` (`hosting` é um array com `target: "production"` e `target: "demo"`, ambos servindo a mesma pasta `dist`, só publicados em momentos diferentes com env diferente).
- Deploy produção: `firebase.cmd deploy --only hosting:production --project podeprev` (build normal, com `.env.local` presente).
- Deploy demo: renomear `.env.local` → `npm run build` → `firebase.cmd deploy --only hosting:demo --project podeprev` → restaurar `.env.local` → `npm run build` de novo (senão a próxima `dist/` fica em modo demo e um deploy de produção subsequente publicaria o build errado sem querer).
- Regras/índices do Firestore são compartilhados pelos dois sites (`firebase.cmd deploy --only firestore:rules,firestore:indexes --project podeprev`) — o site demo nem chega a tocar o Firestore real (roda 100% em memória), então isso só afeta produção.
- (use `firebase.cmd`, não `firebase` — o wrapper `.ps1` global é bloqueado pela política de execução do PowerShell nesta máquina).
- `.env.local` tem as credenciais reais — **nunca commitar**. Se ele for renomeado/removido, o app cai em "modo demonstração" (ver abaixo). **Sempre conferir com `ls .env.local` antes de sair de uma sessão** — é fácil esquecer restaurado depois de gerar um build demo.

## Modo demonstração

Se `VITE_FIREBASE_API_KEY`/`PROJECT_ID`/`APP_ID` estiverem vazios (sem `.env.local`), o app funciona 100% em memória, sem Firebase, com dados fake em `src/demo/seed.ts` e `src/demo/store.ts`. Login com `?demo=professional` ou `?demo=patient` na URL, ou pelos botões de demonstração que aparecem na tela de login quando não há Firebase configurado.

Útil para testar UI rapidamente sem gastar leituras/escritas reais e sem risco de sujar dados de pacientes de teste. **Cuidado**: para forçar modo demo em dev, é preciso renomear `.env.local` temporariamente (setar env vars vazias no PowerShell não funciona — Vite prioriza o arquivo `.env.local` sobre `process.env`). Sempre restaurar o nome do arquivo depois e rodar `npm run build` de novo antes de deployar.

## Arquitetura

- `src/domain/` — funções puras, sem efeito colateral (cálculo de score, fila de ação, sugestão de retorno, checklist de alerta, orientações de cuidado, comparação de evolução). Fáceis de testar isoladas.
- **Modelo híbrido do "Painel de Ação"**: lógica de sistema é FIXA (cálculo de score, classificação, ordenação de prioridade — não editável pelo profissional); conduta, orientações e data de retorno são FLEXÍVEIS (o profissional edita/decide).
- Rotas com `React.lazy()` para code splitting.

## Gotchas importantes do Firestore (já resolvidos, não reintroduzir)

1. **Provabilidade de regras em queries de lista**: se a regra de segurança é `isOwner(x) || isLinkedPatient(y)`, o Firestore exige que **todo campo referenciado nos dois lados** da regra esteja filtrado por igualdade na própria query — senão rejeita a query inteira com "Missing or insufficient permissions", mesmo para dono legítimo. Por isso `listVisitsByPatient`/`listConsentsByPatient`/`listPhotosByPatient` filtram por `professionalId` **e** `patientId` ao mesmo tempo (ver `src/firebase/visits.ts`).
2. **Campos opcionais nas rules**: usar `.get('campo', null)` em vez de acesso direto (`resource.data.campo`) quando o campo pode não existir no documento ainda (ex.: `linkedUserId` antes do paciente vincular a conta) — acesso direto lança erro de avaliação, que a regra trata como "deny".
3. **`undefined` nunca é aceito** pelo Firestore em `setDoc`/`updateDoc`. Use `stripUndefined()` (`src/lib/firestoreSanitize.ts`) na borda de persistência em vez de tratar campo a campo.

## Testes end-to-end

Sem framework de teste automatizado configurado ainda. Verificação é feita manualmente via navegador headless percorrendo o fluxo real (login → paciente → nova anamnese → resultado → salvar → conferir prontuário/painel). Padrão: abrir servidor demo numa porta separada, clicar pelos textos dos botões, nunca usar `location.href`/`Page.navigate` no meio do fluxo (isso recarrega a página e perde o estado do modo demo, que é só em memória).

**Ferramenta**: nesta sessão, Edge + Chrome DevTools Protocol via WebSocket/PowerShell (padrão de sessões anteriores) ficou instável neste ambiente — o processo do Edge lançado com `--remote-debugging-port` encerrava sozinho entre chamadas (possível interferência de outra instância do Edge já aberta pelo usuário, mesmo com `--user-data-dir` isolado). Troquei para **Playwright via `npx`** (não é dependência do projeto, só instalado ad-hoc num `package.json` dentro do diretório de scratchpad, fora do repo): `npx --yes playwright install chromium` baixa o browser, depois um script `.mjs` com `import { chromium } from 'playwright'` roda direto com `node`. Mais estável, screenshots em `page.screenshot()`, `page.textContent('body')` pra asserts simples de texto. Preferir esse caminho a menos que o CDP puro volte a funcionar.

**Pegadinha do login demo por URL**: `?demo=professional`/`?demo=patient` só funciona na **raiz `/`** (passa por `RoleRedirect`, que reage ao estado do `AuthContext` e navega pro lugar certo) — usar em `/patient/login?demo=patient` não redireciona nada, porque `LoginPage` não tem esse efeito, só os botões de demonstração explícitos têm.

**Pegadinha de seletor**: `page.click('text=Buscar')` no `PatientShell` pode bater tanto no item de navegação inferior quanto em qualquer outro texto que contenha "Buscar" na página (ex.: "Buscar avaliação em breve" dentro de uma orientação de cuidado) — escopar por `nav >> text=...` quando o alvo é item de navegação.

## Pegadinhas de UI/teste encontradas

1. `YesNoToggle` (`src/components/ui/YesNoToggle.tsx`) é um toggle de verdade: clicar em "Sim" quando já está "Sim" volta pra `null`. Não é bug funcional pro usuário final normal, mas pode confundir em testes automatizados (clique duplo sem querer limpa a resposta).
2. **Setters de formulário controlado fazem spread de closure, não functional update** (ex.: `StepAnamnesis`'s `set()`/`setDiabetes()`, mesmo padrão em outros `Step*.tsx`): `onChange({ ...value, [key]: v })` usa o `value` capturado no render atual. Se dois cliques em campos DIFERENTES disparam em sequência sem um re-render do React entre eles (só acontece em automação de teste disparando `.click()` sincronamente sem esperar; um usuário real sempre tem esse intervalo), o segundo `onChange` sobrescreve o estado a partir do `value` ainda desatualizado, perdendo a primeira mudança. Não afeta usuários reais. Em testes headless, sempre inserir um pequeno delay entre clicks em campos toggle diferentes do mesmo formulário.
3. **Deploy + chunk hasheado + `firebase.json` com rewrite total (`"source": "**"` → `/index.html`)**: depois de qualquer deploy que mude um arquivo carregado via `React.lazy()`, uma aba já aberta de antes (ou um `index.html` cacheado dentro da janela de `max-age=3600`) pode tentar buscar um chunk antigo que não existe mais — e como o rewrite total intercepta, a resposta vem 200 com HTML em vez de um 404 limpo, o que quebra como "Failed to load dynamically imported module" em vez de erro de rede claro. Não é bug de código; resolve com um hard refresh (Ctrl+Shift+R) na aba afetada. `firebase.json` não tem `"headers"` configurado — index.html e os assets com hash usam o mesmo cache padrão do Firebase.
